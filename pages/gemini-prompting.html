Gemini y prompting

Un modelo generativo puede redactar, resumir, extraer, transformar y analizar información, pero la calidad del resultado depende de la tarea, el contexto y las fuentes que realmente le entregamos. En este curso utilizaremos prompts explícitos y verificables.

1. ¿Qué es Gemini?

Gemini es la familia de modelos generativos de Google. Dentro de Google Cloud puede aparecer integrada en distintas superficies para conversar, trabajar con código, analizar información o asistir en productos como BigQuery.

Para el curso importa más el método que el botón Las interfaces cambian con rapidez. Lo transferible es saber definir una tarea, aportar las fuentes correctas, imponer límites y comprobar si la respuesta está respaldada.

2. ¿Qué es un prompt?

Un prompt es la instrucción y el contexto que entregamos al modelo para obtener una respuesta. No es una “frase mágica”. Un prompt útil reduce ambigüedad y hace explícitas las decisiones que no queremos dejar implícitas.

Prompt débil

“Resume este PDF.”

Prompt controlado

Define qué fuente usar, qué extraer, qué no asumir, cómo tratar faltantes y cómo entregar el resultado.

3. Estructura práctica de un prompt de trabajo

Google recomienda entregar instrucciones claras, contexto y detalles específicos. Para el curso utilizaremos una plantilla de siete componentes que hace visible qué debe controlar el usuario.

ComponentePregunta que responde
Objetivo¿Qué resultado necesito?
Fuentes¿Con qué información puede trabajar?
Contexto¿Para quién o para qué se usará?
Tarea¿Qué pasos debe realizar?
Restricciones¿Qué no debe hacer o asumir?
Formato¿Cómo quiero la salida?
Validación¿Cómo debe tratar faltantes, evidencia e incertidumbre?
No todos los prompts necesitan siete encabezados La estructura sirve para pensar. Una tarea simple puede resolverse con una instrucción corta; una tarea documental, analítica o de auditoría requiere normalmente más control.

4. Objetivo y contexto

El objetivo expresa qué debe conseguir el modelo. El contexto explica para qué se necesita o quién utilizará el resultado. Google recomienda describir el propósito de la tarea porque puede haber varias formas válidas de responder.

Ejemplo
Necesito reconstruir el procedimiento descrito en el documento adjunto para preparar una revisión de Riesgo Operacional.
Mejor que una palabra clave “Procedimiento incidentes” deja muchas decisiones abiertas. Explicar la tarea y su propósito orienta mejor la respuesta.

5. Fuentes: qué información está autorizada

Si una tarea depende de documentos o datos concretos, identifica las fuentes y delimita cuáles puede utilizar el modelo. Esto ayuda a separar evidencia del caso de conocimiento general.

Ejemplo
Trabaja exclusivamente con el documento adjunto. Antes de analizar, identifica la fuente y cualquier fecha o versión que aparezca.
Adjuntar no equivale a verificar Comprueba que la fuente correcta fue realmente incorporada y que su contenido es legible. Un nombre de archivo por sí solo no demuestra qué información contiene.

6. Tarea: indicar qué debe hacer

Cuando la tarea tiene varias etapas, conviene expresarlas en orden. Google también recomienda dividir problemas complejos en solicitudes más pequeñas cuando sea útil.

Ejemplo
1. Identifica el objetivo y alcance del documento.
2. Extrae etapas, responsables, controles y plazos.
3. Señala elementos que no estén especificados.
4. Recién después prepara un resumen ejecutivo.
Orden importa En el método del curso trabajaremos normalmente como FUENTES → COMPRENSIÓN → ANÁLISIS → VALIDACIÓN → ENTREGABLE, en lugar de comenzar directamente con una conclusión.

7. Restricciones: qué no debe hacer

Las restricciones reducen decisiones implícitas. Son especialmente útiles cuando una respuesta plausible pero inventada sería peor que reconocer una limitación.

Ejemplo
No inventes responsables, fechas ni controles.
No completes información ausente usando conocimiento general.
Si un elemento no aparece en la fuente, indícalo explícitamente.
Más razonamiento no corrige una fuente ausente Si el dato necesario no existe en la fuente disponible, la salida correcta puede ser declarar qué falta.

8. Formato de salida

El formato especifica cómo quieres consumir la respuesta. Puede ser una tabla, un resumen breve, un checklist, un informe o una combinación de formatos.

Ejemplo
Entrega:
1. un resumen ejecutivo de máximo 6 líneas;
2. una tabla con etapa, responsable, control y plazo;
3. una lista final de vacíos o preguntas pendientes.
El formato no reemplaza el contenido Una tabla muy ordenada puede contener afirmaciones sin respaldo. Primero controlamos la evidencia; después pedimos una presentación útil.

9. Validación: cómo tratar evidencia e incertidumbre

La validación indica qué debe hacer el modelo cuando no puede comprobar algo. En este curso pediremos separar información explícita, cálculo derivado e interpretación, y declarar faltantes en vez de completarlos.

Ejemplo
Distingue información explícita de interpretación.
Si falta información, escribe “No especificado”.
No atribuyas causalidad ni cumplimiento si la fuente no permite demostrarlo.
Finaliza indicando qué elementos no pudieron verificarse.
Una buena respuesta también reconoce límites En tareas profesionales, declarar “no se puede verificar con esta fuente” puede ser más correcto que producir una conclusión completa.

10. Del prompt débil al prompt controlado

Versión débil

Prompt débil
Resume este PDF.

Versión controlada

Prompt controlado
Analiza el procedimiento adjunto.

Primero identifica la fuente, su alcance y cualquier fecha o versión disponible.

Después reconstruye:
- objetivo;
- etapas;
- responsables;
- controles;
- plazos.

No inventes información ausente. Si un elemento no aparece, escribe “No especificado”.

Distingue evidencia explícita de interpretación.

Finaliza con:
1. un resumen ejecutivo;
2. una tabla del proceso;
3. una lista de vacíos o preguntas pendientes.

El segundo prompt no garantiza una respuesta perfecta, pero hace más fácil comprobar si el modelo siguió la tarea, utilizó la fuente y respetó los límites.

11. Prompting es iterativo

Google describe el prompt engineering como un proceso iterativo: se formula una instrucción, se observa la respuesta y se ajusta el prompt cuando el comportamiento no cumple lo esperado.

Definir tarea y fuentes
↓
Ejecutar prompt
↓
Revisar respuesta
↓
Detectar ambigüedad o incumplimiento
↓
Ajustar y volver a probar
No ajustes para “forzar” la respuesta esperada Ajusta el prompt para hacer más explícita la tarea, el alcance o la validación. Si la fuente no respalda una conclusión, no conviertas esa conclusión en una instrucción.

12. ¿Dónde aparece esto en la Prueba Tipo?

El método de prompting se utiliza en tres momentos distintos:

PDF → texto plano

Gemini recibe una tarea estricta: convertir fielmente el documento sin resumir, interpretar ni completar contenido.

Ejecución del agente

El prompt principal define fuente, tablas, operaciones permitidas, entregables y condiciones de ejecución.

Verificación en BigQuery

Gemini puede recibir una instrucción autosuficiente para generar SQL equivalente que luego debe revisarse antes de ejecutar.

Los prompts definitivos se publicarán literalmente En la sección Prueba Tipo utilizaremos los prompts que ya fueron probados en el flujo real, no versiones reescritas solo para que “suenen mejor”.
